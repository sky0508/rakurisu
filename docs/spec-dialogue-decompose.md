# spec — 対話型・与件分解（シグナル発見）

作成: 2026-08-05 / status: draft（Sora レビュー待ち）
親仕様: `docs/spec.md`（rakurisu 全体）/ 関連: `.claude/skills/lead-harvest/references/signal-catalog.md`

---

## 1. 目的

ふわっとした与件（「営業支援を売りたいがターゲット未定」「成長してる IT 企業」等）を、**リスト化できる検証可能な要件（＝シグナル）**に、**対話で**落とし込む。

現状は `NewJobModal` に与件を 1 回書く → worker が Gemini で 1 発分解（`decompose_brief`）。曖昧な与件ほど 1 発分解は外し、ユーザーはどこで間違えたか分からない。**分解の途中経過をユーザーと協調し、"動いてるもの"を早く見せる**ことで、使い方のイメージが湧く UX にする。

## 2. スコープ

### やること（In）
- 与件が**ふわっとしているとき**の「シグナル発見」を対話で行う専用レーン
- 対話が **N 個（2〜4）の検証可能な仮説**を出し、走らせ方（1 本 / 並列）をユーザーが選べる
- 対話成果物（シグナル/パターン/ソース種類）を既存フローに渡してリスト作成

### やらないこと（Out / 非目標）
- **固定項目の対話化**（用途・件数・コンプラ・収集項目・品質バー）→ 既存フォームのまま。軽実装
- **実ソース URL / レシピの確定を対話でやる**（＝旧 Level 2）→ **既存 worker の②③に統合済みなので作らない**。対話は"方向づけ"まで
- **対話中の先行プレビュー（実クロール 5 件）** → 拡張口。MVP では要件カードのライブ更新で"動いてる感"を出す
- **複数トラック対応の worker 改造** → 不要（1 仮説 = 1 ジョブに写像し、既存の単線パイプラインを N 本走らせる）
- **会話履歴の永続化・再開** → 拡張口（Phase 後段）。MVP はセッション保持で可

## 3. 落とし込みロジック（対話の頭脳）

### 3.0 分解チェーン（lead-harvest signal-catalog が土台）
```
売りたいもの → ペイン（何に困る人に刺さるか）
  → シグナル（そのペインが"外から観測できる"会社の特徴）
  → ソース種類（シグナルが載る公開データの種類）= ここで初めてリスト化できる
  → パターン（A/B/C/D）
```
AI は変換知識（7 軸カタログ）を持ち、ユーザーはドメイン事実（何を売る / どんな客に刺さった）を持つ。対話 = この掛け合わせ。

7 シグナル軸: 求人 / 外部委託 / 成長 / 組織 / 導入・利用 / 業界団体 / 施設立地（各軸に観測ソース例と なりやすいパターンが紐付く。`signal-catalog.md` 参照）。

### 3.1 ムーブ 1 — 現在地の特定
シグナルを出すには 3 情報が要る。**足りないものを優先度順に 1 つだけ聞く**（質問攻めにしない）:

| 優先 | 情報 | 質問 | なぜ最優先 |
|---|---|---|---|
| 1 | 既存顧客の実例 | 「刺さった 2〜3 社の共通点は？」 | 実例からシグナルを逆算できる（最強の一手） |
| 2 | ペイン | 「どんな困りごとに一番刺さる？」 | 顧客がまだいないとき |
| 3 | 商材 | （たいてい最初の一文にある） | — |

### 3.2 ムーブ 2 — ペイン → シグナル変換（コア知能）
ペインを 7 軸に当てて、**各軸で「その会社は外からこう見える」を仮説化**し 2〜4 案提示。
> 例: ペイン「営業力が弱い会社に営業支援を売りたい」
> - ①〈求人〉営業職を募集中＝営業に投資中（ソース種類: 求人ポータル / パターン C）
> - ②〈外部委託〉営業代行の導入事例に載ってる（ソース種類: 代行会社サイト / パターン D）

### 3.3 ムーブ 3 — ガードレール（"ちゃんと設計"の肝）
仮説が雑にならないよう AI に 3 制約を課す:
1. **観測可能性**: 「困ってそう」で止めない。外から観測できる特徴まで落ちてない仮説は却下・作り直し
2. **ソース種類の明示必須**: 各シグナルは必ずソース種類（業界ポータル / 協会名簿 / 求人媒体 等）を伴う。名指せない＝リスト化不可＝無効
3. **母集団爆発チェック**: 業種横断シグナル（求人等）は数万社に膨らむ → AI が**絞り込み軸（業種 or 規模）を逆に問い返す**（「まず食品製造で試します？」）

### 3.4 ムーブ 4 — 収束（複数案のまま）
- 対話は **N 仮説（2〜4）を仮説カードで並べる**。各案 = 〈シグナル軸 + ソース種類 + パターン + 絞り込み軸〉
- **既存レシピにマッチする案は「即試走できます」と告げる**（現 `decompose_brief` のレシピマッチを流用）
- 収束は「1 案に絞る」ことを**強制しない**。ゴールは「小ロットで検証すれば白黒つく N 本」を実行可能な形で並べること（lead-harvest の本来思想）

### 3.5 収束条件（対話をいつ終えるか）
各仮説が「観測可能 + ソース種類あり + 母集団が非爆発」の 3 条件を満たしたら提示可能。ユーザーが仮説を選んで「走らせる」を押した時点で対話終了。

## 4. 出口 — 走らせ方はユーザーが選ぶ

**肝: 1 仮説 = 1 ジョブ**（worker 改造なし。既存の単線パイプラインを N 本）。

1. N 仮説から**走らせる案を選択**:
   - **この案だけ走らせる**（1 本）
   - **選んだ複数を並列で走らせる**（各案が独立ジョブに）
2. 選択後、**共通フォーム 1 枚**で固定項目（用途 / 件数 / コンプラ / 収集項目 / 品質バー）を設定 → N 本に配布（仮説ごとに変わるのはシグナル/ソースだけ）
3. 各仮説 → createJob → 既存フロー（②ソース発見 → ③レシピ生成 → 試走）
4. **「いつ 1 案に絞るか」= 並列試走の取得率を見て勝ち仮説を選ぶ**（lead-harvest Stage 5 評価そのもの）。負け案は archive
5. 同じ対話から生まれた N ジョブは **`hypothesis_set_id` でグルーピング**し、取得率を並べて比較できる

## 5. アーキテクチャ

- **対話 = web 側の同期 Gemini 呼び出し**（低レイテンシの往復が要るため worker poll 経由にしない）。実ソースは幻覚するので対話は"方向づけ"まで（[[reference_llm_url_grounding]]）
- 対話は現状 worker の `decompose_brief`（①）を**人間協調版に置き換える**。実ソース発見（②③）は既存 worker のまま
- 対話が確定した構造化ターゲット（decomp）を job に保存 → worker は**① をスキップして ②③** から
- `GEMINI_API_KEY` を Vercel env に追加（現状 worker のみ保持）
- 幻覚対策: 対話段階では実 URL を名指しさせない。ソースは"種類"まで（例「リフォームの業界ポータル」）。実在ソース確定は worker の Brave 発見

### 頭脳の二重管理について
`decompose_brief` 相当のプロンプト（7 軸カタログ・ガードレール）が web 側にも生まれる。MVP では **web 対話を主経路、worker の `decompose_brief` は「対話を通らない従来フォーム経路」用に残す**（当面二重、落ち着いたら片寄せを検討）。

## 6. データモデル変更（drizzle / Neon）

`jobs` に 2 列追加（いずれも nullable・後方互換）:

| 列 | 型 | 用途 |
|---|---|---|
| `hypothesis_set_id` | uuid nullable | 同一対話から生まれたジョブのグルーピング（比較ビュー用） |
| `decomp` | jsonb nullable | 対話が確定した構造化ターゲット。worker が ① スキップ判定に使う |

`decomp` の中身（案）:
```json
{
  "target": "食品製造業で営業職を募集している会社",
  "signal_axis": "求人",
  "source_type": "求人ポータル",
  "pattern": "C",
  "narrow_by": "業種=食品製造",
  "search_queries": ["...worker ② が使う日本語検索クエリ"],
  "use_existing_recipe": null,
  "hypothesis_label": "①〈求人〉食品製造×営業求人"
}
```

新テーブルは作らない（グルーピングは `hypothesis_set_id` で足りる）。会話履歴の永続化は非目標。

## 7. worker の変更

- `run_decompose`: job に `decomp` があれば **`decompose_brief`（①）をスキップ**し、`decomp.search_queries` / `pattern` / `source_type` を入力に ②（Brave 発見）③（レシピ生成）から実行
- ハンドオフ契約: 対話出力の `decomp` は、現 `decompose_brief` の戻り値と同じキー体系に揃える（`search_queries` 必須。②の入力互換）
- 従来フォーム経路（`decomp` なし）は現状のまま ①②③

## 8. UI

- **入口で二択**（「新規ジョブ」）:
  - ターゲット決まってる → 従来フォーム（1 ジョブ）※今のまま
  - ふわっとしてる → 対話レーンへ
- **対話画面**（quiet-product デザイン言語）:
  - 左: メッセージリスト + 入力欄
  - 右: **要件カード**（分解チェーンの状態: 売りたいもの / ペイン / シグナル軸 / ソース種類 / パターン / 絞り込み軸）をライブ更新 ＝ 動いてる感の主役
  - 収束時: N 仮説カードを並べ、[この案だけ] / [選んだ複数を並列] を選択
- **共通フォーム**: 走らせる案を選んだ後、固定項目を 1 回設定
- **比較ビュー**: `hypothesis_set_id` で束ねたジョブの取得率を並べる

## 9. 検証観点

- 曖昧与件（顧客なし）: 「営業支援を売りたい」→ ペイン質問 → 7 軸で 3 仮説 → 母集団爆発で絞り込み問い返し → 食品製造に絞って 1 仮説確定 → ジョブ生成
- 顧客あり: 「既存 3 社は全部 EC 事業者」→ 逆算でシグナル → 仮説提示
- 並列: 2 仮説を並列 → 2 ジョブ生成 → `hypothesis_set_id` 一致 → 比較ビューに 2 本
- 既存レシピマッチ: シグナルが hotpepper 相当 → 「即試走できます」表示
- 従来フォーム経路が壊れていない（`decomp` なしジョブは ①②③）

## 10. 段階 / 拡張口

- **MVP（本 spec）**: 対話でシグナル発見 → N 仮説 → 1本/並列選択 → 既存フロー + グルーピング比較
- 拡張口:
  - 対話中の先行プレビュー（実クロール 5 件）
  - 会話履歴の永続化・再開・共有
  - 頭脳の片寄せ（web / worker の `decompose_brief` 重複解消）
  - 複数仮説の自動小ロット並列 + 取得率での自動レコメンド

## 11. 未決 / 実装時に詰める

- `decomp.search_queries` を対話（web Gemini）で生成するか、worker ② が `target` から再生成するか（ハンドオフ契約の粒度）
- 共通フォームと仮説選択の画面遷移（1 画面 or 2 画面）
- 要件カードの項目確定（分解チェーン 6 項目でよいか）
